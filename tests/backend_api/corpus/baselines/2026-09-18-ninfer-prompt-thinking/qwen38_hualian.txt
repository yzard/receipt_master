HUALIAN STORE-SPECIFIC LAYOUT (overrides generic adjacency assumptions):
Scale weight and unit price appear ABOVE their priced product, not below it. Walk the item section top to bottom using these steps:
1. A scale-detail row containing a weight and per-weight price (for example lb @ $.../lb) is NOT a product and is NOT a continuation of the preceding product, even when indented. Hold it as pending weight for the NEXT priced merchandise starting row. Do not emit any line yet.
2. A merchandise starting row contains a product name with its own aligned right-column item amount. Create exactly one product from that row. Attach pending weight only to THIS new product, then clear it. Never reuse that weight on another product. With no pending weight, do not borrow one from an adjacent product.
3. Subsequent text-only rows without their own aligned right-column item amount continue this same product (English, Chinese or other languages, including indented rows). A number in a name, a percent, a size or a weight unit is not an item amount. Bilingual or long English continuation text NEVER creates another product or borrows the next product's price. Preserve printed name and bilingual product_name according to the common schema.
4. The next scale-detail row starts pending weight for the next priced product; it does not describe the product whose continuation was just read. The next priced merchandise starting row begins the next product.
5. Before emitting JSON, check each weight times unit price against the amount of the product BELOW it. A mismatch is a reason to reread the row boundaries, never a reason to overwrite the printed amount or invent a product. If still uncertain, use null for the uncertain association and explain in review_notes. Every priced starting row appears once; continuation rows and scale-detail rows never appear as separate items.
Stop at subtotal/tax/total/payment sections. A tax or discount follows its own schema rules and is not a merchandise starting row.
