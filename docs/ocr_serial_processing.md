# OCR 失败诊断与串行任务处理

## 诊断证据

2026-09-17 的旧并发版本全量测试有 11/24 张返回 HTTP 502。该版本同时运行两个收据请求，每个请求又同时调用 Unlimited-OCR 和 PP-OCR；API 将底层错误统一映射成 `inference_error`，OCR 服务当时也没有记录具体的传输异常类型。因此旧日志不足以确定每个 502 的底层异常，不能把猜测的连接错误当成已证实根因。

对这 11 张原照片单独保留两个模型响应的诊断全部成功：每张的 Unlimited-OCR 和 PP-OCR 都返回 HTTP 200；Unlimited 的 `finish_reason` 全部为 `stop`，没有输出截断。失败不能归类成“这 11 张照片模型识别不了”。诊断结果保存在本轮评测归档的 `diagnosis/failed-eleven.jsonl` 和 `diagnosis/summary.json`。

## 当前执行约定

- 手机上传照片、提交任务后立即获得任务编号，仍可继续浏览和编辑。
- backend_api 把任务持久写入 SQLite，playground 使用一个 worker，按创建时间取下一项。其他任务保持 `queued`，当前任务为 `running`。
- backend_ocr 只允许一个收据请求进入推理，多照片按顺序逐张处理。`max_requests` 与 vLLM 的 `max_sequences` 只能为 1，错误配置在启动时拒绝。
- 每张照片先运行 Unlimited-OCR，再运行 PP-OCRv6 medium；两个模型各保留一个实例，权重仍在 OCR 镜像中，不增加容器。
- 两个模型都成功后才返回完整结果。失败会释放处理位置，下一项可以继续，不用缺失一半的结果冒充成功。
- 两份文字和坐标在 API 交叉核验；对齐的中文商品行采用 PP-OCR（包括中文与金额同一行）。差异保留人工核对提示。英文汇总行不会因为 PP 把星号读成一个汉字就被替换成商品。
- OCR 服务记录失败的模型端口、异常类型、HTTP 状态或生成结束原因；日志不记录照片、票面正文或密钥。

## 回归验证

Docker 构建通过 90 项 Rust 测试和 7 项 Python OCR 测试，包括两个任务按顺序处理、排队时普通收据查询响应、失败后释放位置、两张照片均依次经过两个模型，以及 PP-OCR 中文优先和既有店铺/多图解析回归。

实际图片复测与对比图表见 [24 张确认收据评测](confirmed_ocr_comparison.md)。旧并发结果保留，串行结果另存，原数据库收据和确认答案不被测试覆盖。

## 串行实测结论

24/24 返回有效结果，两种模型输出齐全；旧并发版本失败的 11 张全部恢复。总额一致 24/24、明细行数一致 18/24、时间一致 18/24、全部字段一致 7/24；本轮日志无上游调用失败或输出截断。整批 875.02 秒，单请求中位数 71.82 秒包含排队等待。尚有 17 张字段差异，不能把结构有效解读为识别完全正确。
